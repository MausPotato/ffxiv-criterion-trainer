# Ketuduke V4.5 baseline: known limitations

This document records the current behavior. It is not a request to correct or reinterpret the mechanic during migration.

## Rule model

- The four final safe cells come from the eight center-crystal configurations implemented by `referenceSafe()`.
- Outer-crystal movement between the initial and final arrangements is illustrative. `canonicalCrystalFinal()` constrains the final arrangement to the reference safe cells; it does not claim to reproduce the verified in-game trajectory.
- Player displacement, exact damage timing, same-cell resolution, and stack/spread damage areas still require in-game verification.
- A queue or pre-wind positioning mistake can show `YOU DIED`. A failure in the unverified simulation model only produces a warning and does not count as a player death.
- Stack validation currently requires exactly `MT + D1` and `H + D2` in two distinct cells. Spread validation requires four distinct final cells.

## Timing and animation

- Timed mode reveals mahjong after the timer first observes five elapsed seconds and locks input after ten seconds.
- The timer polls every 80 ms. A boundary may therefore be observed on the first poll after the nominal time; from a zero start, the current reveal occurs at 5.04 seconds.
- The UI displays a 24-second buff countdown, but active input timing ends after the ten-second positioning window.
- Each wind animation uses a 2.15-second CSS transition followed by a 2.85-second hold, approximately five seconds per pass.
- Animated and skipped-animation paths are expected to produce the same final player and crystal state.
- Reset, retry, and new-question actions depend on timeout cancellation plus an `epoch` generation guard to prevent callbacks from an older round changing the current round.

## Baseline scope

- These tests observe the existing inline V4.5 script through an in-memory test bridge. The legacy HTML is not edited.
- The fake DOM verifies state, messages, and event flow. It does not claim pixel-level or browser rendering coverage.
- Visual layout and CSS transitions need browser-based screenshot and animation checks in a later migration phase.
